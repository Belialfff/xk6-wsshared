# xk6-shared — обоснование по кейсам, скорости и памяти

Замеры под реальные кейсы нагрузочного тестирования. Все числа получены
бенчмарками (`go test -bench`, Go-часть) и прогоном на генераторе против
боевого Redis (`shared-vs-redis.js`). Ничего не «на глаз».

Окружение замеров:
- Go-бенчмарки: 16 ядер, `go test -bench -benchmem`.
- Redis-сравнение: генератор `nlam0c0xjmt001`, Redis на `nlam0c0xjmt003`
  (та же сеть, боевая инфраструктура), N=5000 операций каждая.

---

## TL;DR — когда что

| Нужно | Инструмент | Разница |
|---|---|---|
| Скорость чтения/записи/забора внутри прогона | **shared** | ~90× быстрее Redis |
| Память при больших данных (пул на все VU) | **shared** | 1 копия в Go, не ×VU |
| Уникальный забор строк на 30k VU | **shared** | без нагрузки на Redis |
| Обмен между генераторами / машинами | **Redis** | shared = один процесс |
| Данные должны пережить рестарт k6 | **Redis** | shared умирает с процессом |
| Координация с внешними системами | **Redis** | напр. общий `regress_act_*` |

Правило: **shared — для скорости внутри одного `k6 run`. Redis — когда данные
должны пережить процесс, шариться между машинами или с внешними системами.**

---

## Прямое сравнение с Redis (реальная инфраструктура)

Одни и те же операции, N=5000. Замерено в двух конфигурациях Redis:
- **сетевой** — Redis на соседней машине (`nlam0c0xjmt003`), боевая сеть;
- **локальный** — Redis на самом генераторе (`localhost`, loopback, без сети).

| Операция | shared (in-proc) | Redis localhost | Redis по сети | shared быстрее (local / сеть) |
|---|---|---|---|---|
| читать скаляр (`get` / `GET`) | **1.8-2.0 µs** | 76.4 µs | 182.0 µs | **42× / 91×** |
| счётчик (`incr` / `INCR`) | **2.2 µs** | 77.6 µs | 182.6 µs | **35× / 83×** |
| уникальный забор (`shift` / `LPOP`) | **1.8-2.0 µs** | 78.6 µs | 197.8 µs | **44× / 99×** |

**Что это показывает:**
- Даже **локальный** Redis (loopback, нулевая сеть) — **~40× медленнее** shared.
  Это неустранимая цена Redis-протокола: сокет + RESP-сериализация + round-trip
  через ядро ОС. Она есть всегда, независимо от сети.
- **Межмашинная сеть удваивает** задержку (77 → 180 µs), доводя разрыв до ~90×.
  То есть примерно половину отставания сетевого Redis даёт сама сеть.
- shared работает в том же процессе (~2 µs, включая границу goja↔Go) — нет ни
  сокета, ни сериализации, ни round-trip.

На 30k VU × тысячи итераций это определяет, упрётся ли тест в собственный
Redis вместо тестируемой системы.

> µs здесь включают накладные goja↔Go на стороне JS. Чистые Go-операции
> (ниже) — десятки наносекунд.

## Кейс 1 — CSV построчно, каждый поток берёт уникальную строку

**Паттерн:**
```js
export function setup() {
    shared.loadCsv('rows', open('data.csv'));   // парсинг в Go, разово
}
export default function () {
    const row = shared.shift('rows');           // FIFO, атомарно, уникально
    if (row === null) return;                    // пул исчерпан
    // ... использовать row ...
}
```

**Загрузка (парсинг в Go, объект `{col: val}` на строку):**

| Строк | CSV-текст | Память в сторе | Байт/строку | Время загрузки |
|---|---|---|---|---|
| 10 000 | 0.2 МБ | 3.7 МБ | ~391 | ~3 мс |
| 100 000 | 1.9 МБ | 38 МБ | ~401 | ~30 мс |
| 1 000 000 | 20.7 МБ | 380 МБ | ~398 | ~300 мс |

**Забор `shift`: 28 нс/оп, 0 аллокаций.**
Проверено конкурентно: 16 горутин разобрали 100 000 строк — **ноль дубликатов**.
Каждый VU гарантированно получает свою строку (мьютекс сериализует снятие).

**Важно:** пул истощается. Если заборов больше, чем строк — залей с запасом,
или используй `random`/`at` (с повторами), или round-robin через `incr`+`at`.

## Кейс 2 — большой JSON (200 МБ, 20k юзеров), вложенный доступ

**Два способа, оба хранят ОДНУ копию в Go (не ×20k VU):**

| Способ | Загрузка | Память в сторе | Доступ | Скорость доступа |
|---|---|---|---|---|
| пул (`loadJsonPool`) | JSON-массив | 219 МБ | `at(i)` → юзер целиком | **14 нс/оп** |
| flatten (`loadJson`) | вложенный объект | 211 МБ | `getPath('123.wallet.limit')` | **19 нс/оп** |

197 МБ исходного JSON → ~210-220 МБ в сторе. Скорость доступа к вложенному
полю **не зависит** от размера данных (14-19 нс на пуле из 20k, как на 100),
0 аллокаций — через границу едет один элемент/лист, не весь массив.

```js
// массив юзеров → пул:
shared.loadJsonPool('users', open('users.json'));
const u = shared.at('users', idx);              // весь юзер, 14нс

// точечно вглубь:
shared.loadJson('users', open('users.json'));   // flatten
shared.getPath('users', '123.wallet.limit');    // 19нс
```

**Ключевое отличие от Redis:** те же 200 МБ в Redis каждый VU тянул бы по сети
(180 µs × размер), плюс JSON.parse на стороне JS. shared держит одну копию в
памяти процесса и отдаёт элемент за наносекунды.

## Кейс 3 — создание / удаление / изменение переменных в рантайме

| Операция | Скорость | Аллокации |
|---|---|---|
| создать (`set` нового ключа) | 84 нс | 2 |
| изменить (`set` существующего) | 28 нс | 0 |
| удалить (`delete`) | 55 нс | 1 |
| атомарно изменить (`update`, под 50 VU конкуренции) | 136 нс | — |

Всё в рантайме теста, потокобезопасно (мьютекс/atomic). Порядок —
десятки-сотни наносекунд, против ~180 µs за любую операцию Redis (в ~1000-2000×
быстрее на запись/изменение отдельной переменной).

| Операция | ns/op | allocs |
|---|---|---|
| `at` (элемент пула) | 14 | 0 |
| `getPath` (вложенный лист) | 19 | 0 |
| `shift` (уникальный забор) | 28 | 0 |
| `set` (изменить) | 28 | 0 |
| `delete` | 55 | 1 |
| `set` (создать) | 84 | 2 |

Загрузки (разовые, в setup): CSV 100k ≈ 30 мс, JSON 200 МБ ≈ 1 c.

## Память — правило

- Данные живут **одной копией** в Go-heap процесса, НЕ умножаются на число VU.
  200 МБ данных = ~210 МБ RAM генератора вне зависимости от 1 или 30 000 VU.
- CSV: ~400 байт на строку-объект. Массив int: ~26 байт/элемент.
  Массив мелких объектов: ~360 байт/объект.
- `pushUnique` держит доп. индекс уникальности (~2× памяти списка).
- `flushAll` освобождает всё; данные умирают с процессом k6.

Сравнение с Redis по памяти: Redis хранит данные в своём процессе, но каждый
VU при чтении **копирует** их к себе по сети. shared — одна копия, доступ по
ссылке/элементу без копирования большого объёма.

## Где Redis объективно лучше (не игнорируем)

- **Между генераторами / машинами.** shared — область одного процесса `k6 run`.
  Distributed-прогон на N тачках общего состояния через shared не получит —
  только Redis.
- **Персистентность.** shared умирает с процессом. Нужно пережить рестарт k6
  или отдать данные в следующий прогон — Redis.
- **Координация с внешними системами.** Пример из этого проекта: общий
  `regress_act_placebet` / `regress_act_settle` в общем Redis — состояние,
  которым обмениваются разные прогоны и, возможно, разные машины. shared так
  не умеет by design.
- **Данные после теста** (очереди на дообработку, результаты) — Redis.

**Гибрид — норма.** Боевой regress-сценарий использует оба: `regress_act_*` в
общем Redis (координация между прогонами — тут Redis незаменим), а внутри
прогона список событий шарится через shared на все VU (скорость, без нагрузки
на Redis на каждой итерации).

## Как воспроизвести замеры

Go-бенчмарки (скорость/память):
```bash
cd k6-extensions/xk6-shared
go test -bench 'BenchmarkUC' -benchmem -run='^$' ./...
go test -run 'TestUC' -v ./...        # память CSV/JSON
```

Сравнение с Redis (на генераторе, Redis рядом):
```bash
REGRESS_REDIS_ADDRS=redis://<host>:6379 \
  ./k6 run --summary-mode=disabled --quiet shared-vs-redis.js
```
(скрипт — `shared-check/shared-vs-redis.js`)
