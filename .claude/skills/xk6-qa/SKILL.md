# QA для xk6-расширений: баги, гонки, утечки

Цель — не «тесты зелёные», а **уверенность, что расширение не уронит генератор
на тысячах VU**. Падение одного VU там — паника всего процесса k6, утечка одной
горутины на итерацию — смерть генератора через час.

Работай по уровням, от дешёвого к дорогому. Каждый найденный дефект классифицируй:
**баг кода** / **баг теста** / **окружение** — и говори об этом прямо. Тест,
подогнанный под баг, хуже отсутствия теста.

> Бенчмарки против существующих решений (k6/ws, k6/experimental/websockets,
> чужие xk6-*) — отдельная задача, в этот скилл пока не входит.

---

## 0. Разведка (обязательно)

1. Найди модуль: `go.mod`, `k6modules.Register("k6/x/...")`, версию k6 в go.mod.
2. Прочитай ВЕСЬ Go-код расширения перед тестами — особенно горутины, каналы,
   мьютексы, `Close`, реконнекты, пуш метрик. Составь список «опасных мест»
   (см. §8) и проверяй их целенаправленно.
3. Посмотри существующие тесты: что покрыто Go-уровнем, есть ли JS-уровень.
4. Тулчейн:
   ```bash
   go version; go env CGO_ENABLED CC
   which gcc clang zig 2>/dev/null
   ```
   `-race` требует **cgo + C-компилятор**. Нет gcc → см. §3.

## 1. Статика

```bash
CGO_ENABLED=0 go vet ./...
CGO_ENABLED=0 go run honnef.co/go/tools/cmd/staticcheck@latest ./...   # тишина + exit 0 = чисто
CGO_ENABLED=0 go run golang.org/x/vuln/cmd/govulncheck@latest ./...
```

govulncheck: отдели уязвимости **своего кода** от дерева зависимостей **k6**
(трассы вида `xk6.init calls modules.init, which eventually calls ...` — это
k6). Последние лечатся версией k6 в сборке, не правкой расширения; HTTP/2
*server*-уязвимости генератору (клиенту) обычно не опасны — так и пиши.

## 2. Тесты Go-ядра и JS-уровня

```bash
CGO_ENABLED=0 go test -count=1 ./...
```

Go-тесты ядра не покрывают **биндинг sobek** — а именно там половина багов:
экспорт конфига, конверсия аргументов, брошенные ошибки, возвращаемые объекты,
сэмплы метрик. Если JS-уровня нет — напиши его через `modulestest`:

```go
import (
    "go.k6.io/k6/js/modulestest"
    "go.k6.io/k6/lib"
    "go.k6.io/k6/metrics"
)

func newJSEnv(t *testing.T, vuContext bool) (*modulestest.Runtime, chan metrics.SampleContainer) {
    rt := modulestest.NewRuntime(t)
    // ВАЖНО: инстанс модуля — ДО MoveToVUContext (он обнуляет InitEnv,
    // а регистрация метрик идёт через InitEnv().Registry).
    mi := new(RootModule).NewModuleInstance(rt.VU)
    _ = rt.VU.Runtime().Set("mod", mi.Exports().Named)   // или Default
    samples := make(chan metrics.SampleContainer, 1<<16)
    if vuContext {
        reg := rt.VU.InitEnvField.Registry
        rt.MoveToVUContext(&lib.State{
            Samples:        samples,
            Tags:           lib.NewVUStateTags(reg.RootTagSet()),
            BuiltinMetrics: rt.BuiltinMetrics,
        })
    }
    return rt, samples
}
// rt.VU.Runtime().RunString(`...`) — синхронный API гоняется без event loop.
```

Что обязательно покрыть на JS-уровне:
- **каждая ветка ошибки конфига** — таблицей `{cfg, ожидаемый фрагмент ошибки}`;
  проверяй текст, а не только факт исключения;
- вызов VU-only API из **init-контекста** (`State() == nil`) → понятная ошибка;
- каждый публичный метод хотя бы раз, включая «после close», «дважды close»,
  «неизвестное имя»;
- конверсии: число из JS приходит `int64` *или* `float64`; отсутствующий ключ
  (`nil` Value) ≠ `undefined` ≠ `null`; `ArrayBuffer` экспортируется как
  `sobek.ArrayBuffer`, `Uint8Array` — как `[]byte`;
- **метрики**: вычитай канал `Samples`, проверь имена, теги, количество.
  Проверяй **число сэмплов**, а не сумму, когда значение может быть 0
  (на Windows задержка внутри процесса часто ровно 0 — разрешение часов);
- обрыв/реконнект через JS-слой: что переотправляется, что нет, сквозные счётчики.

## 3. Гонки

### Нет gcc на Windows
Не ставь в систему — возьми портативный MinGW-w64 в scratchpad:
```bash
URL=$(curl -sL https://api.github.com/repos/brechtsanders/winlibs_mingw/releases/latest \
  | grep -oE '"browser_download_url": "[^"]+x86_64[^"]+ucrt[^"]+\.zip"' | grep -v llvm | head -1 | cut -d'"' -f4)
curl -sL -o mingw.zip "$URL" && unzip -q mingw.zip      # ~250MB, запускай в фоне
export PATH="$PWD/mingw64/bin:$PATH" CGO_ENABLED=1
```
(альтернативы: WSL, Docker `golang` образ). PATH меняй только на время команды.

### Прогоны
```bash
go test -race -count=5 ./...                                  # весь набор
go test -race -count=50 -run 'Close|Reconnect|Overflow|...' ./   # стресс по опасным местам
```
Флаки ловить **циклом по скомпилированному бинарю** (без пересборки на каждой итерации):
```bash
go test -race -c -o rt.test.exe . && for i in $(seq 1 100); do
  out=$(./rt.test.exe -test.run 'TestX' -test.count=1 2>&1)
  echo "$out" | grep -q FAIL && { echo "run $i"; echo "$out" | head -30; break; }
done; rm -f rt.test.exe
```
`-race` расширяет тайминги — флак, который «никогда не бывает» без него,
почти всегда настоящее окно гонки в коде, а не шум. Разбирайся, не ретрай.

Каждое `WARNING: DATA RACE` — смотри оба стека: если оба в `_test.go`
(частое: два читателя одного gorilla-сокета в мок-сервере) — баг теста;
если хоть один в коде расширения — баг кода.

## 4. Утечки

goleak на весь пакет, **без широких игноров**:
```go
func TestMain(m *testing.M) { goleak.VerifyTestMain(m) }
```
Никогда не игнорируй `internal/poll.runtime_pollWait` — именно там висит утёкший
read-loop на сокете. Если что-то чужое (k6 runtime, http-клиент) реально течёт —
игнорируй точечно по `IgnoreTopFunction` с комментарием почему.

**Санити-проверка, что goleak вообще работает** — подсунь заведомую утечку:
```bash
printf 'package X\nimport "testing"\nfunc TestZZLeak(t *testing.T){ go func(){ select{} }() }\n' > zz_leak_test.go
go test -run TestZZLeak ./ ; rm zz_leak_test.go     # должно упасть "found unexpected goroutines"
```
Плюс точечные тесты: N циклов connect→close (в т.ч. конкурентный close из
нескольких горутин), затем `runtime.NumGoroutine()` не растёт.

## 5. Фаззинг байтовых парсеров

Всё, что разбирает байты сервера руками (jsonPath по байтам, VarInt, разделители,
распаковка, поиск ключей, парсинг таймштампов), — получает fuzz-цель. Индексная
арифметика + недоверенный вход = `index out of range` = падение генератора.

Свойства, которые стоит проверять, а не только «не паникует»:
- результат — подслайс входа, не длиннее его;
- на валидном JSON найденное значение — валидный JSON;
- `Decode(Encode(x)) == x` для всех комбинаций кодека;
- декодер не выдаёт пустых сообщений.

```bash
for f in FuzzA FuzzB; do go test -run=NONE -fuzz="^$f\$" -fuzztime=40s ./; done
```
Найденный краш остаётся в `testdata/fuzz/` — он становится регрессионным тестом,
коммитить его.

## 6. E2E на собранном k6

Сборка (Windows-грабли):
- путь только нативный: `--with mod="$(pwd -W)"`, не `/c/...`;
- `xk6 build` падает с немым `exit status 1` → ручная сборка (main.go с
  `_ "модуль"` + `go mod edit -require/-replace` + `go mod tidy && go build`),
  там ошибка видна;
- **`go mod edit -require=x@v` запускай из bash**: PowerShell портит аргументы
  с `@` и `=`;
- проверь пути replace — `go mod tidy` говорит `replacement directory does not exist`.

Прогон: мок-сервер из `examples/`, каждый пример со своими `check()`,
`--quiet` и grep по `checks_failed|✗|level=error`. Затем всплеск на сотни VU.

> Отказы `connectex: actively refused` при одновременном залпе сотен dial на
> Windows — это backlog мок-сервера, не баг расширения. Отличай по
> `connect_success_rate` и по тому, что все подключившиеся итерации зелёные.

## 7. Регрессии

Каждый найденный баг кода → тест, который **падает на старом коде**. Докажи это:
временно верни старое поведение (бэкап файла → правка → прогон → восстановление)
и покажи падение. Только потом фикс.

## 8. Классы багов, характерные для xk6 — проверь каждый

- **Порядок закрытия каналов.** `defer close(done); defer close(events)`
  выполняются LIFO → `events` закрыт раньше `done`; потребитель видит конец
  очереди, спрашивает «соединение умерло?» по `done` и получает «нет» →
  run/next выходят без реконнекта. Сигнал «умер» должен закрываться ПЕРВЫМ.
- **Блокирующая отправка в канал** из read-loop без `select` на `stop` →
  `Close()` виснет, горутина течёт.
- **Несколько писателей/читателей gorilla-сокета.** Один читатель, писатели
  под мьютексом (`WriteControl`/`Close` — исключения, им можно конкурентно).
- **Пуш метрик не с VU-горутины** и после конца итерации; `PushIfNotDone` с
  контекстом VU. Лучше: копить сэмплы в read-loop, пушить с VU.
- **Коллизия имён метрик** со скриптовыми (`ws_*`) — k6 падает при регистрации
  одного имени с другим типом. Свой префикс.
- **Неограниченные кеши/буферы** (regexp, пути, сэмплы, очереди) — нужен потолок.
- `time.After` в цикле → таймеры живут до срабатывания; `NewTimer` + `Stop`.
- `==` на `any` с map/slice внутри → runtime panic. Сравнивать только скаляры.
- **Состояние через реконнект**: что должно пережить (трекинг, буферы,
  счётчики), что пересоздаётся (сокет, горутины), не теряются ли дельты метрик.
- **Отмена контекста VU** — бэкоффы и dial обязаны её уважать.
- **High-cardinality теги** из данных сервера — ограничивать.

## 9. Отчёт

Коротко, по уровням, с цифрами:

| Уровень | Результат |
|---|---|
| vet / staticcheck | … |
| govulncheck | своё: … / k6-зависимости: … |
| unit + JS | N тестов, ×K прогонов |
| race | full ×5, stress ×50 — … |
| leaks | goleak (санити подтверждена) — … |
| fuzz | цели × время — … |
| e2e | примеры, VU, checks — … |

Затем: **найденные баги кода** (что, где `файл:строка`, как доказан, чем
исправлен, регрессионный тест), **баги тестов** (одной строкой), **окружение**
(чего не удалось проверить и почему). Если тот же дефект есть в соседних
расширениях — назови их, но не правь без спроса.
